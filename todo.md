как соотносится Служба-исполнитель с ролями, принадлежностями и прочими атрибуиами пользователя?

Ran 1 shell command

Служба-исполнитель — это не отдельная сущность, а роль. Службами могут быть 5 из 11 ролей компании: PEM, MASTER,
CLEANING, EQUIPPER, INSTRUCTOR. Таблицы служб нет, значение хранится в двух полях:

- fault_types.assignee_role — служба по умолчанию для неисправности;
- repair_requests.assigned_role — текущая служба заявки.

Текстовое поле fault_types.responsible — название службы из классификатора заказчика, в логике адресации из
RepairService и RepairWorkflow оно не участвует.

Как атрибуты пользователя влияют на службу

|         Атрибут          |    Влияет?     |                                                 Как                                                  |
|--------------------------|----------------|------------------------------------------------------------------------------------------------------|
| tenant_id                | да             | Заявка видна только внутри компании                                                                  |
| role                     | да             | Сотрудник входит в службу с таким кодом                                                              |
| extra_roles              | да             | То же, что основная роль: совмещение равноправно, можно быть в нескольких службах                    |
| Роль ADMIN               | да             | Может выполнять действия за любую службу, но уведомления службы не получает, если у него нет её роли |
| active                   | да             | Неактивные не получают уведомлений и не могут выполнять действия                                     |
| Назначение в trip_crew   | только для ПЭМ | Техническая заявка в пути идёт лично ПЭМ рейса (assignee_id)                                         |
| Логин: ИИН или слово     | нет            | Учётная запись подрядчика — обычный пользователь с ролью                                             |
| locale, phone, full_name | нет            | На адресацию не влияют                                                                               |

Депо, организации, подразделения, региона и постоянной бригады у пользователя нет. Отсюда те же последствия, что с
мастерами: две клининговые компании с ролью CLEANING неразличимы, и обе видят заявки друг друга. В tz.entities.md и
tz.functions.md эти атрибуты отмечены (нет).

Как заявка находит исполнителя

1. Служба: берётся assignee_role неисправности, а если его нет — служба по категории (техническая → PEM, уборка →
   CLEANING, экипировка → EQUIPPER).
2. Поправка на этап рейса (RepairService.java:227):
    - в пути: техническая заявка всегда уходит к PEM, даже если в классификаторе указана другая служба;
    - до отправления: служба PEM заменяется на MASTER, остальные службы сохраняются.
3. Доступ: заявка в статусах NEW и DEFERRED видна всей службе (если assignee_id пуст) или только назначенному. Заявка в
   работе видна только взявшему её, и службу уже никто не проверяет.

Что из этого следует

- Инструктор в пути: если неисправность технической категории адресована инструктору, в пути заявка всё равно уйдёт ПЭМ.
  Классификатор здесь не применяется.
- Мастер вне своей службы: он может отклонить новую заявку любой службы, не только свою (RepairWorkflow.java:104). В ТЗ
  это есть: "Служба, мастер депо".
- Снятая роль: если у исполнителя сняли роль, он по-прежнему может завершить взятую заявку, потому что COMPLETE
  проверяет только assignee_id. Если он уволен, заявку завершит только администратор: взять её в работу заново нельзя.

1. GET /wagons/options выбирает тот же SQL, что таблица. Колонки model_type, depot, dbeg_location, wagon_status_type,
   dbeg_status комбо не нужны. Таблицы те же, так что стоимость небольшая, но поля лишние.

   маршрутов. Таблица и панель рейса сейчас не показывают ни остановки, ни км, ни вид маршрута. Это противоречит

Где используется. GET /wagons/options нужен только для подбора вагона при подаче заявки. Цепочка useWagonPick →
fetchTripWagons (вагоны текущего рейса) / findWagons (поиск по цифрам номера) → fetchWagonOptions. Работает в двух

- поле "Вагон" в диалоге заявки на десктопе (WagonPickField.vue);
- мастер подачи заявки на телефоне (RequestWizardPage.vue).

Лишние запросы и join на сервере

3. GET /requests/counts прогоняет весь список целиком, чтобы посчитать заявки по статусам и критичности:
    - выборку с подзапросом числа фото на каждую строку;
    - четыре дополнительных запроса: номера вагонов, сотрудники, рейсы, маршруты.

   Хватило бы одного group by в SQL.
4. Строка заявки — основной запрос плюс 4 пакетных запроса на имена, без N+1. Подзапрос count(*) фото на каждую строку
   оправдан: список показывает число фото.
5. Остановки и км маршрутов считаются в Java по полным строкам route_station, включая станции следования, — порядка 430
   строк в демо на все маршруты. Остановки и км можно получить в SQL (array_agg … filter (where have_stop), max(km)):
   строк из БД придёт столько, сколько маршрутов.
6. RouteNetwork.load() читает все перегоны (~960) и все депо на каждый вызов: при каждом открытии списка следующей
   станции и каждом пересчёте остановок в редакторе. Затем Дейкстра по всей сети. Сеть меняется только в
   администрировании, её можно кешировать с версией.
7. GET /routes/next-stations отдаёт все достижимые станции, это почти все ~900. Комбо с поиском это переварит, но ответ
   большой при каждом открытии.
