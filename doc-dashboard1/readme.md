# Дашборды Жолсерік: новый комплект

Комплект из шести дашбордов и 30 диаграмм ищет неочевидные закономерности в данных системы. Каждая диаграмма
сопоставляет минимум два источника данных. Заголовок диаграммы формулирует вывод, который диаграмма доказывает.

Комплект заменяет набор диаграмм из [../doc-dashboard/todo.md](../doc-dashboard/todo.md).

## 1. Что не так со старым комплектом

1. Старая диаграмма отвечает на вопрос «сколько» по одной-двум таблицам: число заявок по статусам, число вагонов по
   депо. Закономерность между источниками старая диаграмма не показывает: связь заявки с участком пути, с ответственным
   за вагон, с чек-листом приёмки.
2. Большинство старых диаграмм - столбцы и ранжированные списки. Таблица из того же отчёта отвечает на тот же вопрос.
3. Старый комплект построен на прежней структуре БД (`coupling_act`). Новая структура БД даёт источники, которых
   старый комплект не использует: журнал прицепок и отцепок поезда (`train_wagon_change`), пробег вагона за рейс
   (`wagon_run`), журнал ответственных за вагон (`wagon_responsible`), чек-листы (`check_list`), описи экипировки
   (`equip_list`), граф перегонов с координатами (`stage`, `stage_point`), расписание остановок маршрута
   (`route_station.arrival_min`, `departure_min`).
4. Три старые диаграммы ждут нормативов, которых в БД нет. Новый комплект сравнивает показатель с собственной историей,
   с другими депо, с типичным соотношением по всем объектам. Нормативы полезны, но новый комплект от них не зависит.
5. Старая диаграмма показывает показатель, а вывод делает читатель. Новая диаграмма называет вывод в заголовке и
   приводит цифры вывода в колонке «Закономерность».

## 2. Принципы комплекта

- Ракурс, а не таблица: дашборды разложены по ракурсам - время, пространство, вагон, люди, контроль. Одни и те же
  заявки появляются в каждом ракурсе.
- Нормирование: заявки считаются на 100 вагоно-рейсов, на 1000 вагоно-км, на 10 000 км пробега. Длина маршрута и
  число рейсов не искажают сравнение.
- Форма по задаче: календарь - для сезонности, радиальные часы - для суточного ритма, диаграмма Марея - для движения
  поездов, карта - для участков пути, кривые выживаемости - для прочности ремонта, хребтовая диаграмма - для формы
  распределения.
- Цвет по смыслу: одна палитра на комплект; состояние вагона, служба, статус заявки окрашены одинаково на всех
  дашбордах; последовательная шкала - один цвет от светлого к тёмному.
- У каждой диаграммы есть подсказка при наведении, легенда и таблица «Все данные»; светлая и тёмная темы.

### 3.7. Разовые и постоянные диаграммы

Разовая диаграмма находит проблему, которая решается один раз, меняется редко или не зависит от предприятия. После
решения пользователь возвращается к разовой диаграмме при смене расписания, парка или маршрутов.

## 4. Как диаграммы вычисляют данные, которых нет в БД напрямую

- Место подачи заявки в пути (1.3, 2.1, 2.2): телефон не передаёт координаты. Диаграмма вычисляет километр маршрута по
  времени `repair_request.created_dt`: расписание остановок (`route_station`) растягивается на фактическое время рейса
  от `trip.departed_dt` до `trip.arrived_dt`.
- Ответственный за вагон на рейс (4.1): диаграмма берёт запись факта журнала ответственных со стадией «отправление».
  «Найдено после прибытия» - заявка на тот же вагон от другого сотрудника в первые сутки после `trip.arrived_dt`.
- Источник заявки (4.4): заявка по чек-листу - заявка, на которую ссылается `check_list_value.repair_request`;
  заявка по описи - `equip_list.repair_request`; остальные заявки диаграмма делит по роли автора.
- Неисправность пункта чек-листа (5.4): диаграмма берёт неисправность норматива пункта
  (`check_list_item_norm.fault_type`); пункт без неисправности в сравнение не входит.
- Повтор неисправности (3.5): следующая заявка с тем же типом неисправности на том же вагоне, поданная человеком;
  заявки по чек-листу диаграмма не считает повтором, потому что чек-листы повторяются по графику проверок.

## 5. Демонстрационные данные

Страницы открываются в браузере без сервера и без внешних библиотек: файл `index.html` ведёт к пяти дашбордам.

| Файл          | Что в нём                                                                                        |
|---------------|--------------------------------------------------------------------------------------------------|
| `geo.js`      | Сеть перегонов, станции и маршруты; файл строит скрипт `gen-geo.py` из `../db-data`              |
| `gen-geo.py`  | Скрипт сборки `geo.js`: разработчик запускает `python3 gen-geo.py` после изменения `db-data`      |
| `data.js`     | Генератор демонстрационных данных: год работы по маршрутам из `geo.js`                           |
| `common.js`   | Общие функции: шкалы, подсказка, карточка диаграммы, тема                                         |
| `common.css`  | Общее оформление и палитра                                                                       |

Маршруты 1/2, 9/10, 77/78, 655/656 и 659/660 взяты из `db-data/demo/11-route_station.tsv`. Маршруты 51/52, 13/14,
39/40, 71/72 и 23/24 скрипт `gen-geo.py` построил кратчайшим путём по графу перегонов; расписание этих маршрутов
скрипт вычислил по средней скорости 62 км/ч.

Генератор `data.js` закладывает в данные закономерности, которые диаграммы находят:

- холодная волна 12-22 января и праздники увеличивают поток заявок (1.1, 3.1);
- пыльные участки Сары-Шаган - Шу, Кашкантениз - Берлик 2, Актогай - Аягоз, Туркестан - Кызылорда дают окна,
  кондиционеры и уборку (1.3, 2.1, 2.2);
- на участках Мойынты - Сары-Шаган, Мойынты - Балхаш, Есиль - Аркалык, Аягоз - Семей нет связи (1.3, 2.1, 2.2);
- депо Караганды ремонтирует в 1,35 раза медленнее других депо, а последние 45 суток - в 2,3 раза; депо ремонтирует вагоны Астаны
  (1.4, 1.5, 2.3);
- новые вагоны Stadler первые 1,2 года ломаются чаще (3.2, 3.6);
- девять резервных вагонов стоят в парке отстоя больше 110 суток (3.1);
- двое исполнителей технической службы и один исполнитель клининга отмечают «выполнено» через 2-10 минут; после них
  чаще возвраты и повторы (3.5, 4.5);
- три проводника редко пишут заявки сами; неисправности их вагонов находит приёмщик (4.1);
- у ЛНП депо Нурлы Жол постоянные бригады (4.2); нарядчик ставит «любимчиков» на рейс без полного отдыха (4.3);
- пункт чек-листа «Санитарный узел исправен» отмечают нарушением редко при частых жалобах (5.4);
- часть проводников подаёт много необоснованных заявок и завышает важность (6.2, 6.3);
- без плана ответственных после рейса станция принимает вагон через несколько часов, в выходные - в 2,4 раза дольше (6.4);
- поезда депо Алматы меняют состав чаще всего без плана (6.5);
- подстаканники, полотенца и ложки пропадают на отдельных маршрутах (5.1).

## 6. Что нужно решить

1. Место подачи заявки. Диаграммы 1.3, 2.1 и 2.2 вычисляют место по расписанию (раздел 4). Предложение: мобильная
   часть записывает координаты телефона при подаче заявки и при отметке чек-листа; тогда место станет фактом, а зоны
   без связи диаграмма 2.1 покажет точнее.
2. Норма рабочих часов в месяц. Диаграмма 4.3 берёт 168 часов; в БД нормы нет. Нужно решить, где хранить норму:
   константой или у категории сотрудника (`category_type`).
3. Календарь праздников. Диаграмма 1.1 отмечает праздничные дни по списку в `data.js`. Нужно решить, нужен ли
   справочник праздников в БД.
